    在 solvcon 開發比 NumPy 更快的矩陣乘法

    這篇文章記錄我在 solvcon 的 SimpleArray 中開發 matmul_planned() 的過程。目標不是只寫一個處理連續二維矩陣的 GEMM，而是做出一條完整的矩陣乘法路徑：同一套設計要能處理 DOT、GEVM、GEMV、GEMM、任意 leading batch axes、 NumPy-style broadcasting，以及正、負與非單位 stride。

    這項工作的核心是先把運算「規劃」好，再讓 hot loop 專心計算。 複雜的 rank、shape、broadcast 與 layout 判斷在 batch traversal 與 hot loop 前完成，generic executor 拿到的是已經正規化的 M、N、K 與 signed strides。這讓 generic 實作同時保有完整功能與低額外成本， 後續的 specialized routes 也能建立在同一套正確語意上。

    本文進度

    planned matmul 的效能測量與後續執行路徑仍在收尾。這一版先記錄 已經合併到 upstream master 的設計與實作；完整 benchmark 圖表會在 後續補上。

    目前 matmul_planned() 是用來發展與驗證這條新路徑的 opt-in API； Python 的 @ 與既有 matmul() 仍走原本的 implementation。本文談的 效能與語意都只指 matmul_planned()，不把尚未切換的 public operator 混在一起。

    資料布局圖以 self-contained SVG 繪製，點擊可以開啟原尺寸，也能直接下載後 插入 PowerPoint。類別與控制流程只畫穩定的責任邊界，不展開容易隨實作 重構的 private members。

    為什麼需要 planned matmul

    原本的 matmul() 以不同函式分別處理 vector-vector、vector-matrix、 matrix-vector 與 matrix-matrix，而且主要只接受一維或二維輸入。當功能 擴充到 batch、broadcast 和任意 stride 後，如果每條路徑都自行解讀 shape 與 layout，程式很快就會出現重複邏輯，而且 inner loop 也容易背負不必要的 條件判斷。

    matmul_planned() 改成兩個明確的階段。現在的 class names 是 MatmulPlan 與 MatmulExecutor，但真正重要的是責任：

    1. planning 解讀 operands，驗證 contraction dimension，計算 output shape，並記錄 contraction 與 batch traversal 所需的 strides。
    2. execution 綁定 caller 已配置的 output，依照 plan 走訪每個 contraction 並寫入結果。

    入口只需要保留以下穩定順序：

    Text Only
    operation = normalize(lhs, rhs)
output = allocate(operation.output_shape)
execute(operation, lhs, rhs, output)

    這個分界很重要。planning 描述「要算什麼」，execution 負責「怎麼算」。 之後加入不同 kernel 時，不需要再次實作 shape 與 broadcasting 語意。

    flowchart LR
    A["Matmul semantic entry<br/>目前是 matmul_planned()"]
    A --> P["Planning phase<br/>正規化 core axes、batch 與 output semantics"]
    P --> O["配置 output"]
    P --> E["Execution phase<br/>消費正規化後的運算描述"]
    O --> E

    圖中刻意只畫 phases，不列 private structs、members 或 helper methods。 即使內部之後重新分組，「先建立完整運算描述，再執行」仍是這項設計需要 保留的邊界。

    開發順序

    planned matmul 不是一次完成，而是沿著功能邊界逐步擴充：

    1. 先建立二維 matrix-matrix 的 plan 與 signed-stride generic executor。
    2. 加入 equal-shape batch traversal。
    3. 將四種 operand roles 統一，並加入 broadcast batch axes。
    4. 在完整 generic 路徑之上加入 execution dispatch。
    5. 讓可重用的非相容 layout 只 pack 一次，並補上 batched vector routes。

    每一步都保留前一步的 generic correctness。這讓效能技巧可以逐步加入， 而不是把 correctness、broadcasting 與特定 backend 綁成一大塊。

    用一個 contraction 表示四種 matmul

    矩陣乘法最後都可以寫成：

    \[ C_{ij} = \sum_{k=0}^{K-1} A_{ik}B_{kj} \]

    差別只在 M 或 N 是否是由 vector role 引入的 synthetic dimension：

    運算 lhs rhs plan 中的表示 output
    DOT (K,) (K,) M=1, N=1, K (1,)
    GEVM (K,) (K,N) M=1, N, K (N,)
    GEMV (M,K) (K,) M, N=1, K (M,)
    GEMM (M,K) (K,N) M, N, K (M,N)

    vector-matrix 在執行時保留 synthetic M=1，但 output shape 不包含這個 axis；matrix-vector 對 N=1 做相同處理。vector-vector 則沿用 SimpleArray 原本的行為，回傳 shape 為 (1,) 的一元素陣列，而不是 NumPy 的 scalar。

    因此 executor 不需要四份 generic kernel。四種 public semantics 都先變成 同一組 M、N、K，最後進入同一個 contraction loop。

    Broadcasting 不需要展開資料

    NumPy-style matmul 依照 vector 或 matrix role 解讀 trailing core axes； 對 rank 大於等於二的 operand，最後兩個 axes 是 matrix axes，其餘 leading axes 則是 batch domain。兩邊的 batch shape 從右側對齊；每個 axis 必須相等，或其中一邊是 1。

    例如：

    Text Only
    lhs:    (2, 1, 3, 4)
rhs:    (1, 5, 4, 6)
batch:  (2, 1) x (1, 5) -> (2, 5)
core:       (3, 4) x (4, 6) -> (3, 6)
output:                     (2, 5, 3, 6)

    plan 為 output、lhs 和 rhs 各保存一組對齊後的 batch strides。正常的 batch axis 記錄原始 stride；被 broadcast 的 axis 則記錄 0。cursor 往下一個 batch coordinate 移動時，zero-stride operand 的 base offset 不會改變，因此同一塊資料自然被重用。

    這裡沒有建立 (2,5,...) 的 expanded input，也沒有在每個 element 上 重新判斷 broadcasting。plan 只保存 batch domain 與三組 offset mapping， executor 逐一取得 output、lhs、rhs 的 base offset 後，就能重用同一個 contraction。

    Signed stride 是 generic 路徑的能力

    SimpleArray 的 view 不一定是 C-contiguous。transpose、slice、step-two 與 reverse view 都可能產生不同 stride，其中 reverse view 還會使用負值。 如果 generic matmul 預設 rhs 或 vector 是連續資料，結果不只會變慢，甚至會 讀到錯誤位置。

    planned matmul 將四個 contraction strides 明確記錄在 plan 中：

    • lhs_row_stride
    • lhs_inner_stride
    • rhs_inner_stride
    • rhs_column_stride

    generic executor 以 logical data pointer 加上 base offset 開始計算。每完成 一次 multiply-add，只用預先計算的 signed stride 推進 lhs 與 rhs offset：

    C++
    for (ssize_t inner = 0; inner < inner_size; ++inner)
{
    total += lhs_data[lhs_offset] * rhs_data[rhs_offset];
    lhs_offset += lhs_inner_stride;
    rhs_offset += rhs_inner_stride;
}

    同一段程式因此可以處理 contiguous、padded、transposed、step-two 與 negative-stride operands。

    為什麼 generic executor 可以很快

    generic 不代表每次乘加都做通用型別與 shape 判斷。真正進入 hot loop 前， plan 已經把複雜語意消化成少量整數：

    • rank 與 vector/matrix role 只判斷一次。
    • output shape 與 batch broadcasting 只計算一次。
    • batch traversal 使用預先建立的 offset mappings。
    • inner loop 直接讀寫 raw data pointer。
    • signed offsets 以加法遞增，不透過多維索引 API 重新換算。
    • output 是連續配置，row base 可以在外層 loop 重用。
    • 四種 matmul roles 共用同一個小而固定的 loop body。

    換句話說，generic 的「通用」放在 planning 階段；executor 的 hot loop 反而很具體。這也是 planned design 最重要的效能基礎。後面的 dispatch 不會取代 generic，而是在 plan 已知的條件下，選擇是否有更合適的 kernel。

    Dispatch 是下一層，不等於 BLAS

    generic 路徑完成所有語意之後，execution phase 才加入 dispatch。dispatch 負責根據 operation role、problem size、layout、batch reuse 與可用 backend 選擇執行方式；BLAS 只是目前其中一種 route。

    截至本文版本，已合併的 execution routes 包含：

    • 完整 signed-stride semantics 的 generic route。
    • DOT、GEVM、GEMV、GEMM 的 direct BLAS routes。
    • 可重用 operand 的 pack-once 加 BLAS routes。
    flowchart LR
    F["Execution facts<br/>role、dtype、size、layout、reuse"]
    F --> S["Selection policy"]
    S --> P["Optional operand preparation"]
    S --> K["One fixed kernel"]
    P --> K
    K --> B["Batch traversal"]

    這張圖只保留長期穩定的 dispatch phases，不把目前 route 名稱或 private selector 畫進結構。BLAS 是 selection policy 可以選擇的 kernel family， 並不是 dispatcher 本身。

    一次 selection，整批共用

    executor 在進入 batch traversal 前決定 kernel 與需要的 operand preparation。整個 batch domain 共用同一個固定 route，不需要在每個 contraction 裡重新走完整 decision tree。

    如果沒有適合的加速 route，selection 就回到 Generic。因此 generic 是完整 且永遠可用的基線，不是功能殘缺的錯誤處理路徑。

    Direct BLAS 是第一個技巧

    對 BLAS 支援的 value type，selector 會先辨認 DOT、GEVM、GEMV 或 GEMM，再檢查 problem size 與 layout。可以描述成 row-major 或 transposed-compatible row-major BLAS view 的 matrix，能直接交給 BLAS， 不需要 copy。

    小型或 skinny problem、無法直接描述的 layout，以及未達量測 threshold 的 case 仍走 generic。這個選擇不是「有 BLAS 就一定用 BLAS」，因為函式呼叫與 backend setup 對小工作量可能比乘加本身更貴。

    Pack once 是第二個技巧

    如果非相容 layout 的 matrix 會因 broadcasting 在許多 output coordinates 重複使用，executor 可以先把它 materialize 成 row-major storage，再重建 plan。copy 只發生一次，之後所有 contraction 共用 packed operand。

    目前的 matrix-packing route 只處理 shape-broadcast，而且沒有 explicit zero batch stride 的 reused operand。equal-batch matrix 與 explicit zero-stride batch view 保留在 signed-stride generic executor。這是目前 selector 實際合併的能力邊界，不代表其他 layout 無法計算。

    Batched vector routes

    目前 merged implementation 也會為 batched GEVM 與 GEMV 做一次 selection。 相容的 positive-stride vector 可以直接進入 BLAS；不相容但會跨 batch 重用的 vector，則只有在 matrix size、batch size 與總 output work 足以攤平 copy 時 才 pack。

    這些界線集中在獨立的 tuning policy，而不是散落在 contraction loop。 selection 決定 kernel 與 packing，execution 負責照決定執行，generic correctness 保持不變。目前 merged implementation 使用一份 compile-time tuning table，套用到所有支援的 BLAS backend 與 value type；它不是 runtime 或 per-device autotuning。

    測試完整語意，而不只測方陣

    planned matmul 的 differential tests 以 numpy.matmul 為 reference，組合的 範圍包括：

    • float32、float64、complex64 與 complex128。
    • DOT、GEVM、GEMV 與 GEMM。
    • C-contiguous、F-contiguous、padded、negative-stride 與 step-two layout。
    • equal batch、不同 rank 的 right-aligned batch，以及 cross broadcasting。
    • batch axis 與 contraction axis 同時帶有 signed stride。
    • 空的 output axis 與 K=0 contraction。
    • shape mismatch 與 batch broadcast mismatch diagnostics。

    這些測試的目的不是只證明 BLAS case 正確，而是確保每次加入新 route 後， 完整 generic semantics 仍然成立。

    目前做到哪裡

    截至 2026-08-11，upstream master 已經包含：

    • 完整的 generic planned matmul roles。
    • equal batch 與 broadcast batch traversal。
    • signed-stride contraction 與 batch mappings。
    • DOT、GEVM、GEMV、GEMM 的 direct BLAS dispatch。
    • broadcast matrix 的 pack-once route。
    • batched vector 的 direct 與 pack-once routes。

    Strassen kernel 已經獨立合併，但還沒有接入 planned matmul dispatch。 因此本文停在目前真正接入 execution phase 的範圍，不把尚未完成的 selection 說成既有功能。

    實作與開發紀錄可以從以下 commits 開始閱讀：

    • Introduce planned matrix-matrix execution
    • Traverse equal matmul batches
    • Complete generic planned matmul roles
    • Dispatch planned matmul operations through BLAS
    • Pack reused matmul matrices once
    • Tune batched vector matmul routes
