    Benchmark Evidence

    copy 當然有成本。真正的問題是：這份成本要付一次，還是讓每一次矩陣乘法 都繼續繞過 BLAS？

    當一個 strided matrix 被 broadcasting 到多個 batch coordinates，舊 route 會在 每個 coordinate 重跑 generic scalar loop。PR #1256 改成先把無法直接交給 CBLAS、但會被重用的 operand pack 一次，再讓後面的 contractions 共用同一份 contiguous data。兩條 route 的成本可以寫成：

    Text Only
    generic   ≈ B × strided contraction
pack once ≈ one copy + B × BLAS

    其中 B 是重用同一個 operand 的 contractions 數量。這不是「copy 免費」， 而是用一次 copy 換掉 \(B\) 次昂貴的 strided traversal。以下數據檢查的正是 這筆帳。

    Results

    主 benchmark 使用 float32 與 float64 square GEMM，矩陣邊長 S = 8, 12, 16, 24, 32, 64, 128, 256。它分別讓 LHS、RHS，或兩邊同時 broadcast，並為被重用的矩陣建立 negative-inner-stride 與 step-two-inner-stride layouts。

    96 個 workload points 中，S = 8 與 S = 12 的 24 點保留 generic route， 作為未受新 policy 影響的 controls。其餘 S >= 16 的 72 點會走新的 pack-once route，結果是：

    comparison 72 個 affected points
    相對 PR parent 全部較快，speedup 3.30x 到 549.52x
    相對 NumPy 2.5.1 全部較快，speedup 1.11x 到 2.97x

    這 96 個 comparison points 全部通過 correctness 與 sampling audit；最大 relative Frobenius error 是 1.32e-16。因此這份證據支持的是一個明確而有限的結論： 在這台機器、這些 broadcast reuse 與 unsupported layouts 上，S >= 16 的 pack-once route 比 PR parent 和 NumPy 都快。它不把這個結論外推成「所有 matmul 都比 NumPy 快」。

    Method

    這組數字來自 native macOS 26.5.1 arm64、Python 3.14.6、 NumPy 2.5.1 與 Apple Accelerate。所有 BLAS-related thread limits 都設為一， NumPy 與 solvcon 因此在相同 thread setting 下使用 Accelerate。

    每個 workload 比較三個 implementations：NumPy、PR parent，以及 PR #1256。 正式量測前，每個 method 各先做一次丟棄的 preconditioning run。接著六個 balanced rounds 恰好走過三個 methods 的六種 permutations，避免某個 implementation 永遠先跑 或永遠最後跑。

    每一輪中，每個 method 先執行兩個 untimed warm-up batches，再執行 15 個 timed batches。這裡的 timed batch 是一段量測區塊，與 matmul 的 batch axis 無關。區塊內的 inner-loop count 先校準到足夠長的量測時間，再用 elapsed time 除以 call count，得到一筆 per-call estimate。如此不會讓極短 calls 被 timer overhead 主導。

    所以每個圖上的 method point 有 6 rounds × 15 timed batches = 90 per-call estimates。

    報告值是這 90 筆數據的 untrimmed median，不先刪除最快或最慢的 samples。 inputs、conversion、correctness checks 與 warm-up 都不計時；timed region 比較 完整的 np.matmul() 與 matmul_planned() calls，而不是只抽出 GEMM kernel。

    完整輸出有 1,728 筆 JSONL records： 96 workloads × 3 methods × 6 rounds = 1,728。

    每筆 record 保留 dtype、case、size、strides、method order、inner-loop count、 15 筆 estimates 與 numerical error，因此圖上的 aggregate 可以從 raw data 重新計算，而不必相信一張截圖。

    Thresholds

    dispatch threshold 不能只是一個寫進 header 的 magic number。它必須回答： 從哪個 workload 開始，BLAS 節省的計算成本足以償還 dispatch 或 packing？

    PR #1209 先建立 direct BLAS baseline。forced-generic 與 forced-CBLAS 使用相同 inputs，按 generic、CBLAS、CBLAS、generic 的順序執行 calibrated timing chunks；vector routes 另外掃過 1,632 組 shape 與 layout combinations。量到的 routing boundaries 是：

    operation direct-BLAS boundary
    DOT K >= 128
    compact C-layout GEVM K * N >= 729
    other unbatched GEVM/GEMV matrix 的最小 dimension 至少 32
    GEMM M、N、K 的最小值至少 8

    direct BLAS 的大型 controls 也提供一個重要基準：四個 C-contiguous、S = 256 batch GEMM cases 各自獨立重跑五次，solvcon/NumPy runtime ratio 的完整範圍是 0.951 到 1.031，各 case median 落在 0.995 到 1.008。也就是說， compatible layout 直接進入同一個 BLAS backend 時，合理期待首先是 parity， 而不是憑空大幅勝過 NumPy。

    PR #1259 提供了更有用的反例。 32 個 negative-stride vector points 先 pack 被 batch reuse 的 vector，全部快過 NumPy，median speedup 是 6.24x。但 80 個 positive-stride points 可以直接 進 BLAS，雖然全部快過 PR parent，只有 16 點快過 NumPy；整組 median runtime 反而是 NumPy 的 1.06x。

    因此「direct BLAS」不是勝過 NumPy 的充分條件。真正能改變 crossover 的，是 layout、problem size、copy cost 與 reuse count 的組合。PR #1256 的 S = 8, 12 controls 留在 generic route、S >= 16 才 pack，也是同一原則：先量 crossover， 再讓 policy 選 route。

    Limits

    這份 benchmark 不是所有 matmul、所有 layout 或所有機器的排行榜。

    • 它只涵蓋一個 native macOS arm64 環境、一個 Accelerate backend、單一 BLAS thread setting， 以及列出的 float32/float64 square GEMM cases。
    • 1.11x 到 2.97x 是 PR #1256 affected workloads 的結果，不代表 non-square GEMM、DOT、GEVM、GEMV、其他 batch shapes、其他 CPUs 或多執行緒也有同樣 speedup。
    • 549.52x 的 parent speedup 主要描述從重複 generic strided traversal 切換到 pack-once BLAS route，不能解讀成 solvcon 發明了快 549 倍的 GEMM kernel。
    • NumPy 與 solvcon 的 BLAS routes 都使用 Accelerate。這裡證明的是 planning、 layout handling、data movement 與 reuse policy 的 end-to-end 效果，不是 solvcon 的底層 BLAS kernel 比 NumPy 的底層 BLAS kernel 更快。
    • 公開 API 目前仍是 opt-in 的 matmul_planned()；一般 array API 不會因為這份 benchmark 就自動取得相同 route。

    這些限制不削弱結果，反而界定了它可以回答的問題：當 unsupported strided operand 會被 batch broadcasting 重用時，一次 materialization 是否能回本？ 在 PR #1256 測到的 72 個 affected points 中，答案是可以。
